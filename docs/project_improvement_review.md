# 项目改进分析

本文档参考 `Ref_doc.pdf` 中往年课程项目报告的结构，对当前 Expo 项目进行改进空间分析。当前项目已经有比较明确的核心方向：多币种记账、汇率分析、月度交易记录和分类统计。接下来最重要的提升点不仅是继续增加功能，还包括项目定位、架构说明、测试证据、移动端特性和课程报告完整度。

## 当前项目定位

当前应用可以定位为一个个人多币种记账与汇率辅助工具。已有功能包括：

- 添加支出、收入和换汇记录。
- 查看按月份筛选的交易历史。
- 管理多个记账币种。
- 设置默认币种。
- 通过 Frankfurter API 查看汇率趋势。
- 查看收入或支出的分类占比统计。
- 将记账数据和应用设置持久化到本地。

与参考文档相比，当前项目已经具备可运行的功能原型。但如果要作为课程项目展示，还需要进一步补足需求定义、架构说明、UI 展示、测试活动和用户评估等内容。

## 1. 文档层面的改进

参考文档最值得学习的地方是：它把应用描述成了一个完整的工程项目，而不只是一个能运行的 app。当前项目的 `README.md` 主要应作为项目入口说明，用来介绍如何安装、运行和开发项目；它不是正式课程报告。因此，正式文档仍然需要在 `docs/project_report_outline.md` 的基础上继续补充。

建议继续扩展 `docs/project_report_outline.md`，结构可以包括：

- 项目介绍与目标。
- 需求表。
- 已实现功能。
- 应用架构。
- 数据管理方式。
- 外部服务。
- 组件架构。
- UI 设计与截图。
- 测试活动。
- 用户测试与反馈。
- 当前限制与未来工作。

这个项目可以被描述为：面向需要记录跨币种收支的用户，帮助他们管理多币种余额，并结合汇率趋势理解资金变化的移动端工具。

## 2. 需求表

参考文档中使用 R1、R2 等编号清晰定义需求。当前项目也应该补一份需求表，这样功能、代码实现和测试都能对应起来。

建议需求如下：

| 编号 | 需求 |
| --- | --- |
| R1 | 用户必须能够添加支出记录。 |
| R2 | 用户必须能够添加收入记录。 |
| R3 | 用户必须能够添加两个币种之间的换汇记录。 |
| R4 | 用户必须能够按月份查看交易记录。 |
| R5 | 用户必须能够查看不同币种的余额。 |
| R6 | 用户必须能够配置启用的记账币种。 |
| R7 | 用户必须能够配置默认币种。 |
| R8 | 用户必须能够查看汇率趋势。 |
| R9 | 用户必须能够查看收入和支出的分类占比。 |
| R10 | 用户必须能够清空本地记录或生成测试数据。 |
| R11 | 应用应支持离线访问已保存的记账数据。 |
| R12 | 网络不可用时，应用应优先使用已缓存的汇率数据。 |

这些需求可以让项目范围更清晰，也能为后续测试章节提供基础。

## 3. 交易管理功能

当前应用已经支持创建记录和查看月度历史，但交易管理能力还比较有限。

建议改进：

- 增加删除交易记录功能。
- 增加编辑交易记录功能。
- 增加交易详情弹窗或详情页。
- 支持按类型筛选：收入、支出、换汇。
- 支持按金额或日期排序。
- 支持按日期范围筛选。
- 支持根据描述搜索记录。

这是最值得优先增强的功能区域之一，因为它直接影响记账应用的核心体验。参考文档最后的用户反馈中也提到过用户希望可以过滤和排序交易记录，因此这个方向很适合作为基于用户反馈的改进点。

## 4. 换汇记录的数据建模

当前换汇流程会创建两条交易记录：一条支出记录和一条收入记录。这个方案可以运行，但从数据模型上看还不够清晰。

可以考虑增加单独的换汇记录类型：

```ts
type ExchangeRecord = {
  uuid: string;
  fromCurrency: string;
  fromAmount: number;
  toCurrency: string;
  toAmount: number;
  rate: number;
  date: string;
  description?: string;
};
```

如果继续保留“两条交易记录表示一次换汇”的方案，也建议给这两条记录增加共同的 `exchangeGroupId`。这样后续编辑或删除换汇记录时，可以把它们作为一个整体处理。

这样做的好处包括：

- 换汇历史更清晰。
- 编辑和删除更容易实现。
- 统计结果更准确。
- 数据模型章节更容易解释。

## 5. 数据存储与架构

当前项目将记账数据存储在本地 JSON 文件中，将设置存储在 AsyncStorage 中。对于一个本地优先的课程项目原型来说，这是可以接受的。但如果希望项目更完整，可以在架构层面继续加强。

建议改进：

- 在文档中解释为什么选择本地 JSON 存储。
- 明确记录当前数据结构和版本策略。
- 增加数据备份功能。
- 增加 JSON 或 CSV 导入导出。
- 改进写入安全性，降低写入中断导致数据损坏的风险。
- 如果后续查询复杂度提高，可以考虑使用 SQLite。

SQLite 更适合按照类别、日期范围、币种、交易类型等条件查询。但如果时间有限，继续使用本地 JSON 并把它设计和解释清楚，也可以满足课程项目需要。

## 6. 汇率功能改进

当前项目已经使用 Frankfurter API 作为外部服务，这是一个很好的课程项目亮点。接下来可以让汇率功能和记账流程结合得更紧密。

建议改进：

- 显示汇率数据的最后更新时间。
- 增加手动刷新按钮。
- 网络失败时明确提示当前正在使用缓存汇率。
- 使用更友好的错误提示替代纯技术错误信息。
- 支持切换 base currency 和 target currency。
- 在换汇记录页面中，根据当前汇率自动填充第二个金额。
- 在统计页面中解释不同币种交易如何换算为默认币种。

这样汇率页面就不会只是一个独立 tab，而会真正服务于记账和换汇流程。

## 7. UI、响应式布局与主题

参考文档中专门展示了 smartphone UI、tablet UI 和 dark mode。当前项目大多数页面使用固定的浅色主题，例如大量写死 `rgb(253, 247, 245)` 这类颜色。

建议改进：

- 抽出统一的主题文件，集中管理颜色、间距、圆角和字体。
- 支持系统深色模式。
- 优化平板和横屏布局。
- 在 Overview 页面中增加横屏布局，例如左侧显示余额摘要，右侧显示交易列表。
- 检查文字和背景的颜色对比度。
- 为可交互元素补充 accessibility label。
- 考虑国际化支持，或者至少为后续 i18n 预留文本结构。

这些改进会让项目更像一个成熟的移动应用，而不只是一个功能 demo。

## 8. 测试

测试是当前项目和参考项目相比最大的差距之一。当前 `package.json` 中有 lint 脚本，但还没有测试脚本和测试框架。

建议的最小测试计划：

- 测试日期辅助函数和月份 key 生成逻辑。
- 测试余额计算逻辑。
- 测试记账文件 normalize 和迁移逻辑。
- 测试汇率趋势计算函数。
- 测试设置 normalize 和更新逻辑。
- 测试 `CurrencyAmountInput` 组件。
- 测试 `MonthYearPicker` 组件。
- 测试 `TransactionRecordItem` 组件。
- 集成测试：添加一条交易后，Overview 页面能显示该记录。
- 集成测试：添加一条换汇记录后，余额变化正确。

建议工具：

- Jest。
- React Native Testing Library。
- AsyncStorage mock。
- fetch mock，用于模拟汇率 API。

即使测试覆盖率不高，只要有结构清晰的测试章节，也会比完全没有测试更接近参考文档的完成度。

## 9. 移动端设备能力

参考项目展示了 camera、location、notifications 和 orientation 等移动端能力。当前项目更像是一个本地工具型应用，移动设备特性的展示还不明显。

可以考虑增加一个与记账场景贴合的移动端功能：

- 本地通知：每日或每周提醒用户记账。
- 票据照片：为交易记录添加小票图片。
- 数据导出与分享：导出 CSV 或 JSON 并通过系统分享。
- 地点标签：记录消费发生的位置。
- 拍照识别小票金额：如果时间充足，可以作为高级功能。

建议只选择一个设备能力并把它做完整，不要同时加入多个半成品功能。

## 10. 用户测试与反馈

参考文档中包含用户测试，包括任务完成时间和用户反馈。当前项目也可以设计一个规模较小但有效的用户测试章节。

建议测试任务：

- 添加一条支出记录。
- 添加一条收入记录。
- 添加一条换汇记录。
- 修改默认币种。
- 查找某个月份的所有记录。
- 理解统计图表表达的含义。
- 查看某个币种的汇率趋势。

每个参与者可以记录：

- 完成时间。
- 是否成功完成任务。
- 哪些界面元素令人困惑。
- 用户给出的主观反馈。

这样可以为项目的易用性提供证据，也能为未来工作章节提供合理依据。

## 11. 建议优先级

如果时间有限，建议按以下顺序推进：

1. 补充项目文档、需求表、架构说明和截图。
2. 增加交易编辑、删除和筛选功能。
3. 使用 `exchangeGroupId` 改进换汇记录建模。
4. 为核心工具函数和重要组件添加测试。
5. 增加深色模式和平板横屏布局。
6. 增加一个移动端设备能力，例如本地提醒或票据照片。
7. 进行小规模用户测试并记录结果。

## 结论

当前项目已经是一个可以运行的功能原型，但如果要达到课程项目展示的完整度，还需要从“能用的 app”进一步发展为“可展示、可论证、可测试的移动应用”。

参考文档真正值得学习的不是它具体实现了转账、商店或地图功能，而是它把每个功能都放进了需求、架构、UI、测试和用户反馈的完整链条中。当前项目接下来最重要的任务，就是把已有功能整理成一个完整、清晰、可信的工程项目。
